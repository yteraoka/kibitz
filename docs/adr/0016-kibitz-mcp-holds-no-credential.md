# kibitz-mcp に資格情報を持たせない

- **状態**: 採用 (2026-09-22)
- **関連**: PR #23 (`417ea48`) / `docs/worker.md` §8

## 背景

エージェントに、プロンプトが運んだもの以外を尋ねさせたい。
とくにトリアージが差分を絞ったとき (ADR-0013)、
**選ばれなかった 11 個目のファイル**を見る手段が無かった。

素朴な実装は「forge の API を叩けるツールサーバー」である。
しかしそれは、**第三者が書けるテキストを読んだモデルに、forge の資格情報を握らせる**ことになる。

## 決定

**`kibitz-mcp` は別バイナリとし、トークンも forge に到達する手段も持たせない。**

- **worker が、エージェントを起動する前に、自分の資格情報で全部取ってくる。**
  結果をジョブディレクトリのファイル (jobcontext) に書く。
- **`kibitz-mcp` はそのファイルだけを読む。** 他は読まない。
- ツールは 4 つ: `get_pr_metadata` / `list_pr_files` / `get_pr_diff` / `list_pr_comments`
  (ADR-0017 で ADR 用の 2 つが条件付きで加わる)。
- **MCP サーバーとしても、同じハンドラの上で単体 CLI としても動く。**

## 理由

### 設計の要点は、できることではなく**できないこと**である

エージェントが何を言いくるめられて要求しようと、
**答えはこの 1 つのプルリクエストのために既に取得済みのものに閉じている**。
これは「ツールが慎重に実装されているから安全」ではなく、
**到達できる範囲がそもそも存在しない**という形の安全である。

### 置かなかったツールとその理由

- **`get_file` と `search_code`** — ワークスペースに対する `read` と `rg` で足りる。
  同じことをする 2 つ目の経路は、2 つ目の検証すべき境界でもある。
- **`get_related_issue`** — forge 側にまだメソッドが無い。後回し。

### CLI としても動かす理由

2 つある。

- **レビューをデバッグする人が、モデルが見たのと同じ答えを得られる。**
- **エンジンを乗り換えても、自前のツールはそのまま使える** (ADR-0003)。

### 失敗を JSON-RPC エラーにしない

ツールの失敗は `isError` を立てた content で返す。
**「そんなファイルは無い」に対して行動できるのはモデルであり、
プロトコルエラーはモデルに届かない。**

`internal/mcp` はツールプロバイダに必要な 3 メソッドだけを実装し、
**残りは拒否する**。持っていない能力を名乗らない。

### 検証

実物の opencode 1.18.31 から接続し、healthy と報告されることを確認した。
プロトコルも直接叩いた — `initialize`、`initialized` 通知、`tools/list`、
`tools/call` の成功と失敗の両方、`ping`、そして壊れた行。

## 影響

- worker は jobcontext を**エージェント起動前**に書く。
  取得できなかったものはツールからも見えない。
- トリアージで絞られたレビューでも、
  **プロンプトは選ばれた差分、jobcontext はプルリクエスト全体**を持つ。
- `KIBITZ_MCP_CONTEXT_BIN` でバイナリの場所を指定する。
