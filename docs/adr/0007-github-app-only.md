# 認証は GitHub App のみにし、PAT の経路を捨てる

- **状態**: 採用 (2026-09-21)
- **関連**: `9256f2a` / `9b5790d` / PR #6 / `docs/security.md`

## 背景

当初の設計には GitHub App と Personal Access Token の両方の経路があった。
PAT は「手軽に試せる」という理由で入っていた。

## 決定

**GitHub App のみを実装する。PAT の経路は設計から落とす。**

- JWT を標準ライブラリで署名し、installation token と交換する。
- token はキャッシュし、期限前に更新する。
- kibitz 自身の bot アカウント名は**設定させず、自分で導出する**。

## 理由

### PAT を捨てた理由

PAT は**個人に紐づく**。その人が退職すれば止まり、
その人の権限すべてがボットの権限になり、
監査ログにはその人がやったように見える。
「手軽に試せる」ために持つには代償が大きい。

App なら権限はインストール単位で絞れ、token は 1 時間で切れ、
投稿は「アプリがやった」と表示される。

2 経路あると**どちらでも動くように書く**ことになり、
権限モデルの前提が 2 つになる。片方に寄せたほうが安全側に倒しやすい。

### bot アカウント名を設定させない理由

`bot_logins` は `"<app-slug>[bot]"` の形で手書きする必要があり、
**間違えても何も起きない**。気づくのは kibitz が自分のコメントに返事を始めたとき。

ループ検査の両側とも、今は自分で導出する。

- **サーバー側はアプリ ID で照合する。** GitHub は issue コメントを
  書いたアプリを `performed_via_github_app` で教えてくれる。アプリ ID は
  設定済みで、しかも秘密ではない (アプリの設定 URL の数字) ので公開サーバーが持ってよい。
  名前ではなく ID で照合すれば、**アプリをリネームしても壊れない**。
- **ワーカーは訊く。** アプリの鍵を持っているので `GET /app` で slug が分かり、
  起動時に `"<slug>[bot]"` を導出する。訊けなくても致命的ではない
  (サーバー側がすでに落としている)。

`bot_logins` は任意・加算の設定として残す。
どちらでも拾えないアカウント (リネーム後に残った旧名など) があるため。
レビューコメントがまさにその例で、GitHub は issue コメントにはアプリを書くが、
レビューコメントには書かない。

## 影響

- GitHub Enterprise Server は payload からインスタンス URL を導出するので、
  追加設定なしで動く。
- webhook secret は**複数受け付ける**。ローテーション中に配信を落とさないため。
- 署名検証は**パースの前に raw body に対して**行う。
