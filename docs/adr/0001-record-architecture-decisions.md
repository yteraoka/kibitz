# 設計上の決定を ADR として残す

- **状態**: 採用 (2026-09-22)
- **関連**: PR #26 / `internal/worker/references.go`

## 背景

kibitz の設計判断は、これまで 2 か所に散っていた。

- **コミットメッセージ** — 理由が最も濃く書かれている場所だが、`git log` を読む人にしか届かない。
- **`docs/*.md`** — 現在の仕様は書いてあるが、**なぜそうしたか**と**何を捨てたか**は落ちている。

落ちる情報には具体的な価値がある。たとえば「webhook のリプレイ窓を既定で無効にした」のは、
5 分窓にしたら GitHub の Redeliver が黙って 204 を返したからで、
署名で認証済みの payload に時刻の窓を足しても二重実行は防げない (それは delivery id の仕事) と判断したため。
この経緯を知らない人は、リプレイ窓が無いことを**やり残し**として再実装しにかねない。

そして kibitz 自身がレビューする側でもある。
理由を知らないレビュアーは、理由が存在しないものとしてレビューする。

## 決定

**設計上の決定は `docs/adr/` に 1 決定 1 ファイルで記録する。**

- ファイル名は `NNNN-英語の短い要約.md` (連番、ゼロ埋め 4 桁)。
- 先頭行の `# ` 見出しは**決定の内容そのもの**を書く。「〜について」ではなく「〜する」。
- 見出しの直後にメタ情報 (状態・決定日・関連 PR / コミット / ドキュメント) を置く。
- 本文は **背景 / 決定 / 理由 / 影響**。検討して捨てた案があるなら、捨てた理由まで書く。
- 決定が覆ったら、**元の ADR は書き換えず**に状態を `置き換え` にして新しい ADR を指す。
  ADR は仕様書ではなく履歴なので、過去の判断が消えては意味がない。

書くのは**決定**だけにする。仕様は `docs/*.md` の仕事で、ここに両方置くと必ず食い違う。

## 理由

### なぜ見出しを決定文にするか

kibitz は ADR の**パスとタイトルだけ**をプロンプトに載せる (ADR-0017)。
つまり見出しの一行が、そのままレビュー時の索引の一行になる。

```
- docs/adr/0010-data-and-instruction-positions.md — データの位置と指示の位置を分ける
```

「ADR-0010 について」では索引として何も伝わらない。
見出しは**存在を知らせる**と同時に**検索語彙を渡す**ので、決定文を書くほうが働く。

### なぜ連番か

日付順でもトピック順でもなく連番にすると、
「ADR-0010 を前提にしている」と他所から指せる ID が手に入る。
タイトルが変わっても、ファイルを移動しても、番号は動かない。

## 影響

- `docs/adr/**/*.md` は `worker.DefaultReferenceDocs` の先頭パターンなので、
  **このフォルダに置いた時点で、以降のレビューの索引に載る**。設定は要らない。
- 索引の上限は 50 件 (`maxReferences`)。超えた分は索引に出ないが、
  エージェントは `read` / `grep` で読めるので見えなくなるわけではない。
- タイトルは 90 文字で切られる (`maxTitleRunes`)。一行に収まる長さで書くこと。
