# エージェントエンジンに OpenCode を採用する

- **状態**: 採用 (2026-09-21)
- **関連**: `9bdbb5c` / **`docs/agent-engine.md` (比較の詳細)**

## 背景

`reviewer.Engine` の実装として実際にモデルを動かすものが要る。
候補は OpenCode と pi の 2 つだった。詳しい比較表は `docs/agent-engine.md` にある。

## 決定

**OpenCode を主軸のエージェントエンジンとする。**

ただし `reviewer.Engine` インターフェースは、**pi でも実装できる粒度**に保つ。
エンジンに要求する能力を次の 6 つに限定する。

作業ディレクトリの指定 / ツールと権限の制限 / システムプロンプトの差し替え /
セッションの継続 / 構造化出力 / 実行イベントの取得。

## 理由

**決め手は MCP サーバー対応が要件だったこと。**

pi は設計思想として MCP を持たない。「CLI ツール + skills を使え、
必要ならエクステンションで自作せよ」という方針で、これは怠慢ではなく選択である。
だが要件が「第三者が提供する MCP サーバー (Jira、Sentry、社内検索) をそのまま繋ぐ」なら、
pi では MCP クライアントを TypeScript で実装し、
プロセス管理・再接続・ツール定義の変換まで自前で持つことになる。
Go 中心のこのプロジェクトに、別言語のコア部品を抱え込む話になる。

OpenCode は設定に書くだけで済む。

### pi が優れている点も記録しておく

公平に言えば、pi のほうが良い点は 3 つあった。

- **読み取り専用の保証**: `--tools read,grep,find,ls` は `bash`/`write`/`edit` を
  完全に外せる。OpenCode の `permission` は表現力が高い分、設定ミスの余地が大きい。
- **Go からの統合**: pi の RPC モード (双方向 JSONL) は非 Node 言語からの統合を明示的に想定している。
  OpenCode は「毎回プロセス起動」か「HTTP サーバーを立てる」の二択。
- **ハング**: OpenCode は `"ask"` が残っていると承認待ちで固まる。
  対策は全権限を `allow`/`deny` で決め切ることと `--auto`。

MCP 一点でこれらを上回ったという判断である。

## 影響

- 権限は**ジョブごとに kibitz が生成する**。リポジトリから読むことはしない
  (プルリクエストが自分のレビュアーの権限を広げられてはいけない)。→ ADR-0010
- `"ask"` を残さない。全権限を `allow`/`deny` で決め切り、`--auto` を付ける。
- **`kibitz-mcp` は MCP サーバーとしても単体 CLI としても動く**ように作る (ADR-0016)。
  エンジンを乗り換えても自前ツールは使い回せる。
- 乗り換えを検討すべき条件は `docs/agent-engine.md` の「pi に切り替えるべきケース」にある。
