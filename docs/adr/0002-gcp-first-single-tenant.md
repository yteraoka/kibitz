# GCP を主軸にし、単一組織を前提に作る

- **状態**: 採用 (2026-09-21)
- **関連**: `9bdbb5c` / `docs/architecture.md` / `docs/roadmap.md`

## 背景

当初の実装計画は、GCP と AWS を同時に一級市民として扱い、
マルチテナント (複数組織を 1 つのデプロイで賄う) も視野に入れていた。

どちらも「後から足すのは大変だから最初から」という理屈で入っていたが、
実際に動かす環境は 1 つの GCP プロジェクト、1 つの組織だった。

## 決定

**GCP を主軸のクラウドとし、単一組織を前提に設計する。**

- キュー / 状態ストア / Blob ストアは**インターフェースとして残す**が、
  実装は Pub/Sub・Firestore・GCS を先に作る。
  SQS / DynamoDB / S3 は後続フェーズに送る。
- 設定モデルに**テナント分離の概念を入れない**。
  リポジトリの許可リスト (`KIBITZ_ALLOWED_REPOS`) が境界のすべて。
- クレームチェック (大きい payload を Blob に逃がす仕組み) だけは早い段階に残す。
  **生の payload を保持する要件がどのみちこれを必要とする**ため、後回しにしても得がない。

## 理由

インターフェースは残すのに実装を後回しにするのは、一見すると中途半端に見える。
しかし**コストが非対称**だった。

- インターフェースを後から切るのは、呼び出し側を全部書き換えることになる。高い。
- インターフェースがある状態で 2 つ目の実装を足すのは、1 ファイル増えるだけ。安い。

だから境界だけ先に引き、実装は要るときに書く。

マルチテナントは逆で、**後から足すコストより、要らないのに持つコストのほうが先に来る**。
テナント ID が設定・イベント・状態キー・ログのすべてを貫通し、
1 組織しかない環境ではその全部が常に同じ値になる。
読む人はそれが意味を持つと思って読むので、誤解を生み続ける。

## 影響

- `internal/queue` / `internal/store` / `internal/blobstore` はバックエンドを
  `KIBITZ_*_BACKEND` で選ぶ形になっている。AWS 実装はここに足せばよい。
- Terraform は GCP のみ。AWS 対応をやるならモジュールは新規。
- レビュー対象の範囲は許可リストで決まる。
  1 つのデプロイを複数組織で共有する運用は想定外で、やるなら設計からやり直し。
