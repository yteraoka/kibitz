# キューは Cloud Pub/Sub、順序キーはプルリクエスト単位にする

- **状態**: 採用 (2026-09-21)
- **関連**: `9c5c6c8` / `docs/queue.md`

## 背景

webhook を受けるサーバーと、レビューを実行するワーカーは分かれている。
レビューは数分かかるので、webhook のリクエストの中ではできない。
間に何を置くかという話。

## 決定

**Cloud Pub/Sub を使い、順序キーをプルリクエスト単位にする。**

- publish するときの ordering key は「プラットフォーム + リポジトリ + PR 番号」。
- subscription には **dead letter policy を必須**とする。
- ack 期限はジョブタイムアウトより長く延長し続ける。
- lease するメッセージ数は、ワーカーが同時に開始できる数を超えない。

## 理由

### 順序キーがプルリクエスト単位である理由

同じプルリクエストに対して push が 2 回続くと、イベントも 2 つ出る。
順序が保証されないと、**古いコミットのレビューが新しいコミットのレビューを追い越す**。
レビュー本文には「レビュー対象: `abc1234`」と書いてあるので、
読む人には古い結果が最新に見える。

逆に、**別のプルリクエスト同士を順序付ける理由は無い**。
キーを PR 単位にすると、順序を守りつつ並列度が上がる。

### 順序付き publish が失敗したら再開が要る

Pub/Sub は、あるキーの publish が失敗すると、
**そのキーの以降のメッセージを全部拒否する**。
放置すると 1 つのプルリクエストだけが黙って死ぬ。
だから失敗時は明示的に `ResumePublish` を呼ぶ。

### dead letter が任意でない理由

このビルドがデコードできないメッセージ (未来の schema、壊れた payload) は、
何度再配信しても同じ結果になる。ループさせずに落とす先が要る。
落とす先が無いと、詰まったメッセージが lease を占め続ける。

### ack 期限をジョブタイムアウトより長く保つ

期限が切れると Pub/Sub は 2 台目のワーカーに同じメッセージを渡す。
**1 つのプルリクエストに 2 台が同時にレビューを投稿する**のが最悪の結果なので、
実行中は延長し続ける。

## 影響

- Pub/Sub クライアントが新しい Go を要求したため、toolchain が Go 1.25 に上がった
  (その後 1.27)。
- テストは `pstest` (インプロセスの fake) で動かし、**どこでも実行できる**ようにした。
  ただし fake は順序を忠実に再現しないので、
  **順序のテストは実エミュレータの CI ジョブでのみ実行**する (`emulator` ジョブ)。
- ローカルは `make up-pubsub` でエミュレータ + トピック + 順序付き subscription が立つ。
- キューの意味論 (at-least-once、失敗時の再配信、dead letter) は
  インメモリ実装でも守っている。バックエンドを差し替えてもワーカーは変わらない。
