# サーバーが受信時にコメントへリアクションし、そのために絞った資格情報を持つ

- **状態**: 採用 (2026-09-27)
- **関連**: [ADR-0014](0014-worker-pool-and-self-managed-scaling.md) / [ADR-0019](0019-run-repository-code-in-a-credential-less-job.md) / [security.md](../security.md#サーバーが持つ資格情報) / [review-flow.md](../review-flow.md)

## 背景

コメントで kibitz に頼んでから、最初の反応が返るまでが長い。ワーカーは 0 台まで
縮むので ([ADR-0014](0014-worker-pool-and-self-managed-scaling.md))、
起動を待つと**1 分近く何も見えない**。頼んだ人には「届いたのか」が分からない。

これまでサーバーは**forge の資格情報を 1 つも持っていなかった**。署名を検証して
publish するだけで、書き込む手段が無い。インターネットに公開されているのは
サーバーのほうなので、これは意図した形だった。

## 決定

**コメントが publish されたら、サーバーがその場で 👀 (Azure DevOps では like) を付ける。**

- 付けるのは**publish に成功したコメントだけ**。kibitz 宛てでないコメント、
  自分の発言、許可されていないリポジトリには付けない (ポリシーを通ったあとなので)
- 先に 202 を返して flush し、**そのあとで**リアクションする。forge は応答を
  待たない。リアクションの失敗はログとメトリクスに残すだけで、配送は失敗にしない
- `KIBITZ_REACTION_TIMEOUT` (既定 3 秒) で打ち切る
- `KIBITZ_REACTIONS=false` (Terraform では `server_reactions = false`) で止められ、
  **止めればサーバーは forge の資格情報を読まない**

そのためにサーバーはワーカーと同じ変数で資格情報を受け取る。**GitHub では
発行するトークンを `issues: write` と `pull_requests: write` だけに絞る**。
GitLab と Azure DevOps には絞る仕組みが無いので、ワーカーと同じトークンになる。

## 理由

**ワーカーで付けると意味が無い。** ワーカーが動き出した時点で「開始しました」の
コメントが出る。欲しいのはその前、「受け取った」の合図である。

**別サービスに分ける案は採らなかった。** Pub/Sub の push サブスクリプションで
小さなサービスを起こせば、公開されたサーバーに資格情報を置かずに済む。
ただしリアクション 1 つのためにサービス・サブスクリプション・IAM が 1 組増え、
そのサービスもコールドスタートを待つ。サーバーは既に温まっていて、
署名とポリシーを通ったあとでしか資格情報を使わない。
公開面が広がるなら、この判断を見直す。

**goroutine に逃がさない。** Cloud Run はリクエストが終わったインスタンスへの
CPU 割り当てを止めてよい。応答後に始めた処理は走らないことがある。
だからハンドラの中で、応答を flush してから同期的に付ける。
`Content-Length: 0` を先に宣言するのは、forge が本文の終わりを待たずに
応答を完結とみなせるようにするため。

## 絞ることで守れるもの、守れないもの

**守れる:** サーバーのメモリやログからインストールトークンが漏れても、
そのトークンでは**push できない** (`contents` を持たない)。マージもできない
(マージには `contents: write` が要る)。

**守れない:**

- **App の秘密鍵そのもの。** 鍵があれば、App に許されたすべての権限で
  トークンを発行し直せる。サーバーが乗っ取られたら、鍵は漏れたものとして扱う
  ([runbook.md §1-3](../runbook.md#1-3-失効させるべきとき))
- **絞ったトークンでもできること。** コメント、Issue と PR の編集・クローズ、
  **承認を含むレビューの投稿**。ブランチ保護が App の承認を数える設定なら、
  それは承認として効く
- **GitLab / Azure DevOps のトークン。** 絞れないので、漏れればワーカーのものが
  漏れたのと同じ (コードの読み書き)

## 影響

- サーバーの SA に、秘密鍵 (と有効なら GitLab / Azure DevOps のトークン) の
  `secretAccessor` が付く。`server_reactions = false` なら付かない
- 鍵やトークンのローテーションは**サーバーのリビジョンも更新する**必要がある
  ([runbook.md §1-2](../runbook.md#1-2-交換の瞬間があるもの))
- サーバーから forge の API への外向き通信が発生する。kibitz 宛てのコメント 1 件に 1 回
- `kibitz_reactions_total{outcome="failed"}` が増えていれば、付いていない。
  レビュー自体には影響しない
- Azure DevOps の work item のコメントには付けられない (like の API が無い)。
  今は work item のイベントを受けていないので、実際には起きない
