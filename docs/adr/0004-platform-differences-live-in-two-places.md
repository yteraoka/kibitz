# プラットフォーム差は正規化イベントと forge の 2 か所に閉じる

- **状態**: 採用 (2026-09-21)
- **関連**: `604353b` / `9b5790d` / PR #12 / PR #13 / `docs/event-schema.md`

## 背景

GitHub、GitLab、Azure DevOps に対応する。
3 つは webhook の形も API も認証方式も違うが、kibitz がやることは同じ
「プルリクエストを読んで、レビューを書く」である。

素朴に書くと、この差はコードのあらゆる場所に漏れる。
ポリシー判定が GitHub の payload の形を知り、
ワーカーが GitLab の `iid` と `id` の違いを知り、
プロンプト生成が Azure DevOps の用語を知る、という状態になる。

## 決定

**プラットフォーム差を入口と出口の 2 か所だけに閉じ込める。**

| | 場所 | 役割 |
| --- | --- | --- |
| 入口 | `internal/event` + `internal/webhook/*` | 各 webhook を**1 つの正規化イベント**に落とす |
| 出口 | `internal/forge` | プルリクエストを読む / レビューを投稿する |

その間 (`internal/policy`、`internal/worker`、`internal/reviewer`) は
**プラットフォームを知らない**。

さらに `internal/event` の schema は**バージョン付け**する。

## 理由

### なぜイベントを正規化するか

webhook を受けるのは公開されたサーバー、レビューするのはキューの向こうのワーカーで、
間にキューがある。キューに入れる形式は事実上そこが契約になるので、
どうせ 1 つに決めなければならない。なら生の payload ではなく、意味のある形にする。

結果として `internal/policy` (何をキューに入れるか) がプラットフォーム非依存になり、
GitLab 対応は「webhook を 1 つ足す」だけで済んだ。実際にそうなった (PR #12)。

### なぜ schema をバージョン付けるか

デプロイ中は**新旧のワーカーが同時にキューを読む**。
古いワーカーが新しいメッセージを引くと、無限に再配信されて詰まる。
バージョンがあれば「これは未来のビルドのメッセージだ = 恒久的に配送不能」と判定でき、
リトライではなく dead letter に送れる。

### `Validate` が全部のエラーを集める理由

正規化のバグは 1 つ直すと次が出る、を繰り返しがち。
最初の 1 つで止めずに全部返せば、1 回で直せる。

### forge のインターフェースを小さく保つ

`Client` は 8 メソッドしかない。プルリクエストの取得、差分、比較、コメント一覧、
レビュー投稿、サマリの upsert、ファイル読み取り、プラットフォーム名。
ここに「GitHub の Checks API を使う」のようなものを足すと、
他の 2 つが実装できない穴が開く。**3 つ全部で意味を持つ操作だけを入れる。**

## 影響

- **イベントはスナップショットとして信用しない。** ジョブ実行時には古くなっているし、
  Azure DevOps の payload はそもそも信用できない。だから `PullRequest()` で取り直す。
- 新しいプラットフォームを足す作業は、`internal/webhook/<name>` と
  `internal/forge/<name>` の 2 つを書くことに等しい。
- GitLab 対応で判明したとおり、**この 2 か所には調べ直しが要る**。
  GitLab は Standard Webhooks 方式で署名するようになっており、
  重複排除に使うべきキーは event UUID ではなく delivery id だった
  (設計メモの記述が 2 点間違っていた)。記憶ではなく公式ドキュメントを読むこと。
