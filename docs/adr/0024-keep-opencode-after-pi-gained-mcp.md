# pi 1.0 が MCP に対応した後も OpenCode を使い続け、pi は試作エンジンで検証してから判断する

- **状態**: 採用 (2026-10-02)
- **関連**: ADR-0003 (採用理由のうち MCP の部分を置き換える) / `docs/agent-engine.md` / ADR-0015 / ADR-0018 / ADR-0021

## 背景

ADR-0003 で OpenCode を選んだ決め手は、**pi が MCP を持たないこと**だった。

その前提が崩れた。pi は 1.0 (2026-10-01) で MCP クライアントを組み込みで持つようになった。

- `mcp.json` の `mcpServers` (他の MCP クライアントと同じ形) で、stdio と streamable HTTP を宣言できる
- `env` / `headers` の中の `${VAR}` は pi のプロセス環境から置換される
- `enabled: false` でサーバーを個別に止められ、`toolExposure` でツール単位に `hidden` にできる
- プロジェクトの `.pi/mcp.json` は project trust を与えたときだけ読まれ、
  ヘッドレスでは `--no-approve` で明示的に拒否できる

ADR-0003 は「MCP 一点で pi の利点を上回った」としていたので、決定を見直す必要があった。

## 決定

**エンジンは OpenCode のままにする。** ただし理由を入れ替える。

- 「pi は MCP を持たない」は理由から外す。
- 新しい理由は**乗り換えの費用**、**pi の MCP 実装の成熟度**、**pi の上流の方向性**の 3 つ。
- `reviewer.Engine` の裏に **pi の試作エンジン** (`KIBITZ_AGENT_ENGINE=pi`) を足し、
  下の「未検証の点」を実機で確かめてから改めて判断する。

## 理由

### MCP は決め手でなくなったが、乗り換える理由にもならない

MCP について言えば、両者は**ほぼ互角になっただけ**である。
kibitz の使い方 (デプロイ側が宣言し、`{env:NAME}` で資格情報を注入し、ジョブごとに config を書く — ADR-0015)
は pi でもそのまま表現できる。OpenCode から移す手順も pi の公式ドキュメントにある。

残る pi の利点は ADR-0003 に記録した 3 つ (読み取り専用の保証、RPC モード、承認待ちで固まらない) で、
変わっていない。

### 乗り換えの費用は、すでに OpenCode に払ってある

`internal/reviewer/opencode` は約 3,700 行 (テスト込み) あり、
失敗の診断、モデルカタログ、イベント解析、プロセス管理を持つ。
ADR-0021 では、ループバックを `NO_PROXY` から外せないこと、カタログ更新の宛先などを
**OpenCode の実機に対して**確かめた。pi に移るとこれをやり直すことになる。

### 読み取り専用の保証が、pi でも自明ではなくなった

ADR-0003 では「`--tools read,grep,find,ls` で `bash` を完全に外せる」ことを pi の強みとした。
1.0 の MCP は、既定ではツールを直接モデルに見せず、**codemode** (モデルが書いた JavaScript から
ツールを呼ぶサンドボックス) 経由で呼ばせる。ドキュメントには

- codemode 公開の MCP サーバーが繋がると codemode が**自動で有効になる**
- codemode からの呼び出しは**有効なツールの組み合わせに依存しない**

とある。`--tools` で絞ったとき codemode から `bash` 等に届かないかは、文面からは確定できない。
`"autoEnableCodemode": false` と `exposure: "direct"` で避けられる見込みだが、未検証である。

### MCP は出たばかりで、上流の方向性に懸念が増えた

pi の MCP は 0.99 から 1.0 にかけて入ったばかりで、kibitz のような無人実行での実績がまだ無い。

pi は 2026-04 に Earendil に買収された。1.0 では自社の AI ゲートウェイ (Radius) への導線が増え、
インストール時のテレメトリとプロバイダ帰属ヘッダーは**既定で有効**
(`PI_TELEMETRY=0` で止める)。新規コントリビュータの issue / PR を自動で閉じる運用も続いている。
上流に直してもらう前提では使えず、自分たちで抱える覚悟が要る点は ADR-0003 のときと同じである。

### 捨てた案: すぐに pi へ乗り換える

決め手が消えた以上、ADR-0003 で pi の利点としたものだけが残る、という見方もできる。
だが上の codemode の件で「読み取り専用の保証」は確かめるまで利点と言えず、
RPC モードの利点は [worker.md](../worker.md) の `run` / `attach` の二実装で実用上ほぼ埋まっている。
確かめていない利点のために、確かめ終えた実装を捨てる理由は無い。

## 影響

- 未検証の点 (pi に切り替える前に、試作エンジンで確かめること):
  1. `--tools read,grep,find,ls` と MCP を併用したとき、codemode や `tool_search` から
     許可していないツールに届かないか。`autoEnableCodemode: false` と `exposure: "direct"` で閉じられるか
  2. codemode 経由の入れ子の呼び出し (`parentToolCallId`) を、ADR-0018 の計測と
     イベント解析がどう数えるべきか
  3. ADR-0021 のプロキシに、pi 本体 (Node) が `NODE_USE_ENV_PROXY=1` 無しで従うか。
     モデルカタログの更新など、pi 自身の通信が `PI_OFFLINE=1` で止まるか
  4. Vertex AI で、ADC による Gemini に加えて Claude と Model Garden の第三者モデル
     (`vertex-maas/...`、ADR-0008) が使えるか
  5. `~/.pi/agent` (設定・認証・trust・セッション) をジョブごとの使い捨てディレクトリに隔離できるか
- 上の 5 点がすべて満たせても、乗り換えるかどうかは改めて決める。満たせないものがあれば OpenCode を続ける。
- `docs/agent-engine.md` の比較表と「pi に切り替えるべきケース」は、この ADR に合わせて書き直した。
