# エージェントの外部アクセスは、ワーカー内の inspection するプロキシを通す

- **状態**: 採用 (2026-09-28)
- **関連**: `internal/egress` / `docs/configuration.md` の「外部アクセスの制御」 / ADR-0010 / ADR-0015 / ADR-0016

## 背景

レビューのエージェントは第三者が書いたテキストを読む (ADR-0010)。
言いくるめられたときに**どこへ行けるか**と、実際に**どこへ行ったか**の
両方が必要になった。

それまであったのは、opencode の permission (`webfetch` を拒否し、`bash` を
`git` / `rg` に絞る) と、MCP を三層で宣言する仕組み (ADR-0015) だけだった。
どちらも「どのツールを持つか」を決めるが、**ツールがどこに繋ぐかは決めない**。
remote MCP サーバーや、local MCP サーバーが内部で取りに行く先は、
何の記録も残らなかった。

## 決定

**エージェントのプロセスの HTTP(S) を、ワーカーの中で動くプロキシに通す。
既定では無効 (`KIBITZ_EGRESS_PROXY`)。**

- **ジョブごとにセッションを開く。** `127.0.0.1` の別ポートで待ち受け、
  opencode に `HTTPS_PROXY` などを渡し、ジョブが終わったら閉じる。
  ログの行にはジョブの `event_id` が付く
- **許可リストと拒否リストで決める。** ルールは `host[:port][/path]`。拒否が優先。
  許可リストが空なら拒否リスト以外はすべて許可する (記録だけする)
- **TLS inspection を既定にする。** ワーカーが起動時に自分専用の CA を作り、
  エージェントのプロセスにだけそれを信頼させる。これでパスが判定にもログにも使える
- **1 リクエスト 1 行をログに出す。** 記録するのは宛先・パス・クエリの**名前**・
  結果・バイト数・時間。ヘッダ、クエリの値、ボディは記録しない
- **loopback とメタデータサーバーは通さない。** loopback は設定に関わらず

## 理由

### プロセスの外ではなく、ワーカーの中に置く

Squid や mitmproxy をサイドカーにする案があった。Cloud Run の worker pool でも
サイドカーは置けるが、そうすると

- ログに `event_id` を付けられない。どのジョブの通信かは、同時に走る
  ジョブの間で区別がつかない
- CA の秘密鍵を 2 つのコンテナの間で受け渡すことになる
- 設定と検証が kibitz の外に出る。起動時にまとめて設定の誤りを報告する
  (`KIBITZ_*` の方針) ことができない

Go の標準ライブラリで足りる (`httputil.ReverseProxy`、`crypto/tls`、
`crypto/x509`) ので、依存も増えない。

### ジョブごとにポートを分ける

1 つのプロキシを共有し、`Proxy-Authorization` でジョブを見分ける案もあった。
クライアントがプロキシの URL に埋め込んだ資格情報を送るかどうかは実装次第で、
送らないクライアントがあると**全部が拒否される**。ポートを分ければ、
クライアントに何も求めずにジョブと通信が対応する。

### CA はインスタンスごとに作り、鍵を書き出さない

運用者が CA を用意して Secret Manager に置く案は捨てた。その CA は
**どのサーバーにもなりすませる鍵**で、長命で、漏れたら信頼している側を
すべて探して回ることになる。インスタンスごとの CA なら、鍵はそのプロセスの
メモリにしか無く、信頼しているのはそのプロセスが起動したエージェントだけで、
再起動で消える。

### 許可リストが空なら「全部許可 + 記録」にする

空なら全部拒否、のほうが安全側に見える。しかし有効にした瞬間にモデルへの
通信も止まり、全レビューが失敗する。**まず記録を取り、実際に使っている宛先を
見てから許可リストを書く**のが現実的な導入順で、それを既定の挙動にした。
空のまま動かしていることは起動時に警告する。

### パスが見えないときは、見えない側に倒す

inspection しない宛先 (無効にしたとき、または証明書をピン留めするクライアント向けの
`KIBITZ_EGRESS_TLS_PASSTHROUGH`) では、パス付きのルールを評価できない。
そこでは

- パス付きの**拒否**ルールがそのホストにあれば、**ホストごと拒否**する
- パス無しの**許可**ルールが無ければ拒否する

inspection 自体を無効にした設定にパス付きのルールがあれば、起動時に拒否する。
書いたルールが効いていないのに効いているように見えるのが、いちばん悪い。

### 許可リストがあれば内部アドレスを許す

許可リストが空のときは、プライベート / loopback / リンクローカル宛ての接続を
**名前解決の後で**拒否する。そうしないと、エージェントはワーカーの
ネットワークから届くものに何でも届く。許可リストがあれば、通る宛先はすべて
運用者が名前で書いたもので、社内の Jira のような内部の宛先はむしろそのために書く。

### `Host` は CONNECT に合わせる

inspection した接続の中のリクエストは、`CONNECT` した先にしか転送しない。
`Host` ヘッダが違えば 421 で拒否する。許可されたホストへの接続を開いて、
同じ CDN の後ろにある別のホストを `Host` で指す (domain fronting) のを防ぐ。

### これは壁ではない

プロキシが効くのは、プロセスが `HTTPS_PROXY` に従うからである。
自分で直接繋ぐバイナリは迂回できる。**強制はネットワーク層が担う**
(`docs/security.md` の「egress をネットワーク層で制限」)。
このプロキシの役割は、その手前で**何に触ったかを記録すること**と、
行儀のよいクライアント (opencode と、Node / Bun の MCP サーバーの大半) を
ルールで止めることにある。ネットワーク層は宛先の IP しか見えず、
パスも、どのジョブの通信かも分からない。両者は役割が違う。

### 検証

- 単体テストで、inspection した転送・パスでの拒否・`..` を含むパス・
  許可リスト外の `CONNECT`・`Host` の不一致・トンネル・passthrough・平文 HTTP・
  内部アドレスの拒否・セッションを閉じたときのトンネルの切断を確認した
- 実機で、curl・Node 24 (`NODE_USE_ENV_PROXY=1`)・Bun 1.2 の `fetch` が
  プロキシに従い、CA を信頼し、許可は 200・拒否は 403 になることを確認した
- ワーカーのイメージの Node (`node:22-slim`、v22.23.3) でも、`fetch` と
  `https.get` の両方が `NODE_USE_ENV_PROXY=1` でプロキシに従うことを確認した。
  **このフラグが無いと Node はプロキシの変数を無視して直接繋ぎ、ログにも残らない**。
  フラグを付けると stderr に `EnvHttpProxyAgent is experimental` の警告が出るが、
  動作には影響しない
- ワーカーのイメージ (opencode 1.18.31) の中で、kibitz の `opencode.Runner` に
  プロキシをつなぎ、Vertex AI の Gemini で実際のレビューを最後まで走らせた。
  許可リストは `*.googleapis.com` だけ
  - モデルへのストリーミング (`streamGenerateContent`) 32 件と ADC のトークン更新
    (`oauth2.googleapis.com/token`) が inspection 付きで通り、すべて `event_id` 付きで記録された
  - 許可外の remote MCP サーバーは `CONNECT` で拒否され、opencode はそのサーバーを
    使えないものとして扱ってレビューを続けた
  - opencode 自身のモデル一覧の更新 (`models.opencode.ai`) とプラグインの install
    (`registry.npmjs.org`) も拒否されたが、どちらも失敗してもレビューに影響しない
- **loopback を常に除外する理由も実機で見つけた。** opencode 2.x は自分の
  サーバーと `http://127.0.0.1:<port>` で話し、Bun は `NO_PROXY` に無いと
  これもプロキシに送る。プロキシが拒否すると、opencode は再試行を続けて止まらない

## 影響

- `KIBITZ_EGRESS_PROXY` を有効にしたら、許可リストにモデルの宛先
  (`*.googleapis.com`) を必ず入れる
- エージェントの環境の最後にプロキシの変数と CA のファイルが付く。
  継承した `HTTPS_PROXY` よりも優先される
- `kibitz_egress_requests_total{outcome}` が増える。ホスト名はラベルにしない
  (拒否された宛先はエージェントが言いくるめられて書いた任意の名前で、
  系列が際限なく増える)
- `kibitz-runner` (実装モードのビルドとテスト) は対象外。別のジョブで、
  資格情報を持たない (ADR-0019)
